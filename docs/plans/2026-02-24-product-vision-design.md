# Deskhand 产品愿景：从 0 到 1

> 这份文档记录了 Deskhand 产品最初的构想过程，以 Q&A 的形式还原从零开始的头脑风暴。
> 它是所有后续设计文档的根基——回答「我们为什么要做这个产品，它到底是什么」。

---

## Q1: 最初萌生做 Deskhand 的念头，是因为什么？

我自己在践行且观察到身边很多人，我们都在使用 Claude Code 去做很多编程以外的事情——增长运营、PRD 编写、PPT 编写、Excel 编写、内存清理、桌面整理、相册分类等等，用途太多了。

我是从 2024 年 12 月开始用 Cursor，我是产品出身，所以本身就对代码不是很敏感，对于其他用途更感兴趣，所以一直在用 Cursor、后来用 Claude Code 去做各种事情。我非常相信这个能力远远超出编程写软件，它所能实现的事情对于很多非技术者都有帮助。

在 Cowork 诞生前我只是有模糊的想法。Claude 的 Cowork 诞生后我意识到，豆包这样的客户端产品也远远不够，因为 Cowork 就是一个「普通人的 Claude Code」，能用它大大扩展自己的能力边界和能力深度。未来我相信是超级个体的未来，不再是 specialized，而是一个人完成一个很大 scope 的 judgement to ship。所以我也想去做一款 Cowork 那样、甚至比 Cowork 更好的产品。

**核心洞察：**

1. Claude Code 的底层能力让它有非常大的能力扩展空间，几乎可以做任何电脑办公能做的事
2. Claude Code 对于非技术的普通人不是最优解
3. 未来是超级个体的未来
4. 超级个体未来会越来越需要 Claude Code-like 的能力去扩展自己的能力 scope，完成一整套事情的交付

## Q2: 非技术用户使用 Claude Code 时，最大的障碍是什么？

### 1. 安装部署门槛高

普通人不容易接触到、不容易通过命令行去下载安装部署。

### 2. 命令行界面劝退

CC 的命令行界面让人望而却步，只能用指令和提示词来操作，几乎零引导，让用户难以深入使用它的功能。

### 3. 功能决策面向技术者

CC 的功能设计主要以技术者为主。只要一个产品面向的用户群体不同，功能决策上必然会有差异，用户 A 和用户 B 不可能对于所有功能的需求一致。具体体现在：

- **目录即工作区** — 技术者习惯项目目录结构，普通人文件随便丢桌面或下载文件夹，根本不会做目录管理
- **输出不可视** — 生成的 HTML/代码/图片以原始格式呈现，非技术者习惯于所见即所得——我看到一张图、我看到一个网站，而不是一串 base64 或者 HTML
- **权限模型太技术** — bash 执行、文件写入这些权限概念对普通人没有意义，他们不理解「为什么要我同意执行一段 shell 命令」
- **工具命名面向开发者** — Read、Write、Bash、Edit 这些工具名是开发者词汇，普通人更理解「打开文件」「保存」「运行」
- **上下文管理是隐性的** — 技术者理解 token 限制、context window，普通人不知道为什么聊着聊着 AI 就「忘了」之前说的话
- **反馈全是文本流** — 没有进度条、没有状态指示，技术者习惯看 log 滚动，普通人需要「正在处理中… 50%」这样的视觉反馈

### 4. 是工具，不是助理

CC 以「用户主动使用和编辑」为主。但普通人需要的不是一个工具，而是一个助理。助理不是在吩咐的时候才去做，而是主动知道「我能做什么」。因为普通人往往也表达或者想不清楚自己需要什么。大部分情况下，助理给老板端杯水或者打印文件是常识需求——CC 不会主动给用户提供这种价值。

### 5. 用户表达困难，缺乏引导

CC 不能很好地帮助用户讲清楚需要什么。它会去问，但问了之后的文字回答依然可能讲不清。哪怕有 playground 这样的插件也需要用户主动使用。

用户更需要的是：「我去请一位设计师帮我做家里的设计，你给我很多样板、你带我参观、你给我建模 demo、你告诉我我的品味不够好。」就好像买家具，我不会一上来就准确知道「我要红色的木制的 60 厘米高的椅子」，而是大概知道我要「传统家具」。

这里很大的差异是——在 CC 里「技术者是权威的，是主人」；在 desktop agent 里「普通人是说不清楚的，是需要纠正的，是需要引导的」。

### 6. 错误信息不可理解

普通人看到报错直接就慌了，不知道是自己的问题还是 AI 的问题，也不知道该怎么办。技术者看 stack trace 能定位原因，普通人只看到一堆乱码般的文字，本能反应就是「完了，是不是我搞坏了什么」。

### 7. 成果散落找不到

做完了不知道东西在哪。技术者打开文件树就能找到，普通人会问「你刚才帮我做的那个东西呢？」生成的文件散落在目录里，没有一个「这是你的成果，点这里查看」的入口。

### 8. 不知道它能干什么

CC 没有能力边界的展示，普通人不知道「原来你还能帮我整理照片」，只会用自己碰巧知道的那一两个用法，大量能力被浪费了。

### 9. 多步骤任务容易断

普通人让 AI 帮忙做一件稍微复杂的事（比如「把这个文件夹里的照片按日期分类然后每个月做一个相册」），中间出了问题不知道做到哪了、哪步成功了哪步失败了，也不知道怎么让它「从断的地方继续」。

## Q3: 用一句话定义 Deskhand 到底是什么？

> 一个住在你电脑里的助理，它能操作你的文件、理解你的需求、主动帮你把事情做完。

## Q4: 目标用户是谁？

> 以下按「谁更需要这个产品」排序。排序依据：任务对文件操作的依赖程度、现有工具的服务缺口、重复性工作的自动化潜力、用户的技术门槛。

### 1. 行政/财务助理

When 月底要把几十张发票照片整理成报销表，I want to 让 AI 识别每张发票的金额日期并自动填进 Excel，so I can 一小时搞定原来要花一天的对账工作。

> 排序理由：日常工作几乎全是重复性文件操作，技术能力最低，被现有 AI 工具服务得最差，时间节省最显著。

### 2. 小公司创始人

When 我要给投资人准备 BP，数据散落在 Excel、备忘录和微信截图里，I want to 让 AI 直接读取这些文件并生成一份演示文稿，so I can 把时间花在打磨故事线而不是整理数据和排版上。

> 排序理由：什么都要自己干，时间极度稀缺，需要跨多种文件类型工作，最需要一个「什么都能帮忙」的助理。

### 3. 跨境电商卖家

When 我要把 50 个商品上架到新平台，每个都需要翻译标题、优化描述、调整图片尺寸，I want to 让 AI 批量处理这些重复性工作，so I can 一天上完架而不是一周。

> 排序理由：大量批量化、模式化的文件操作，现有工具完全无法满足，自动化 ROI 极高。

### 4. 独立教师/培训师

When 我要为下周的课程准备教案和练习题，I want to 告诉 AI 教学目标后它帮我从我的素材库里组织内容并生成学生用的 PDF，so I can 把备课时间从 4 小时压缩到 1 小时。

> 排序理由：高频刚需，每周都要做，涉及素材整理和文档生成，且教师群体普遍非技术背景。

### 5. 自由摄影师

When 我拍完一场活动有 500 张照片散落在多个文件夹，I want to 让 AI 帮我按场景筛选、批量调整尺寸加水印然后导出，so I can 当天就把精修图交给客户而不是花一整晚手动处理。

> 排序理由：明确的批量文件操作需求，工作流清晰，AI 介入后效率提升直观可衡量。

### 6. 产品经理

When 我需要快速出一个可交互原型给团队评审，I want to 描述功能后 AI 直接生成一个我能点击操作的 demo，so I can 用真实体验而不是静态截图来推动决策。

> 排序理由：强烈的「所见即所得」需求，但技术能力相对较高，部分人已经在用 Cursor/CC。

### 7. 房产中介/销售

When 我要给不同客户发定制化的房源推荐，I want to 让 AI 根据客户需求从我的房源表里筛选匹配并生成带图片的推荐文档，so I can 同时服务更多客户而不是一个个手动挑选和排版。

> 排序理由：个性化文档生成需求明确，但工作场景更偏移动端，桌面使用频率可能较低。

### 8. 大学生

When 期末要交数据分析报告但我不会配 Python 环境，I want to 直接告诉 AI「帮我分析这份数据」它就能跑代码出图表，so I can 专注在分析结论而不是被技术环境卡住。

> 排序理由：需求真实且痛点明确，但年轻用户学习能力强，更容易适应现有工具，且付费意愿较低。

### 9. 律师/法务

When 我收到一份 80 页的合同需要审阅并标注风险条款，I want to 让 AI 读完整份文件后高亮关键风险点并生成摘要，so I can 快速定位问题而不是逐页阅读。

> 排序理由：需求高价值，但行业合规要求高，对 AI 操作文件的信任门槛也高，早期不容易切入。

### 10. 退休人员/数字化新手

When 我想把手机里几千张家庭照片按年份和人物整理成相册，I want to 用最简单的方式告诉 AI「帮我整理照片」它就知道该怎么做，so I can 不用学任何软件就把几十年的回忆整理好。

> 排序理由：最需要「零门槛」的体验，但获客难度最大，对新软件的接受度最低，适合作为远期愿景而非早期目标。

## Q5: Deskhand 和市面上的 AI 产品（Cowork、ChatGPT、豆包等）最本质的区别是什么？

### 1. 它就在你电脑里干活，不是在云端帮你做完再让你下载

别的 AI 是在它们自己的地方帮你做东西，做完了你得下载回来。它们不认识你的电脑，不知道你桌面上有什么文件，你要用什么得自己一个个传上去。Deskhand 直接在你的电脑上干活——它能去你的桌面找到那个 Excel，能去你的下载文件夹翻出上周的发票，能一次处理你硬盘里 500 张照片。你不需要传任何东西，因为它就在你家里。

> 这是门票——没有这个能力就别玩了。

### 2. 同样的能力，但你不需要懂技术就能用

Cowork 和 Claude Code 也能在你电脑上干活，但它们的界面、用词、操作方式都是给懂技术的人设计的。Deskhand 做的事情一样，但你看到的、摸到的、理解的方式完全不同。同一台发动机，一个装在赛车里需要你会开手动挡，一个装在家用车里你踩油门就走。

> 这是真正的壁垒——能力一样但体验不同，这决定了谁能用谁不能用。

### 3. 它会主动找事做，不是等你吩咐

现在所有 AI 产品都是你说一句它做一句。但普通人的问题是：我都不知道该让你做什么。Deskhand 会自己看到「你桌面很乱」然后问你要不要整理，而不是等你想到「我应该让 AI 帮我整理桌面」。

> 这是最难做到的——别人可以抄界面但很难抄产品理念。

## Q6: MVP 应该让用户能做到什么？

用户用一句模糊的话描述需求，Deskhand 直接在用户电脑上完成了一件事，并且把成果展示给用户看。

整个过程里用户不需要：上传任何文件、理解任何技术概念、做任何配置。

具体来说，第一个版本至少要让用户能走通这条路：

1. 打开 Deskhand（像打开任何 app 一样，双击就行）
2. 用自然语言说一件事（比如「帮我把下载文件夹里这个月的 PDF 整理到一个新文件夹里」）
3. Deskhand 去做了，中间用户能看到它在干什么（不是看代码，是看「正在扫描文件…找到 12 个 PDF…正在移动…」）
4. 做完了，直接展示结果（「已整理完成，12 个文件移到了这里，点击查看」）

用户第一次体验完会想：「这东西真的能动我电脑上的文件，而且我什么都不用懂。」

这比任何花哨的功能都重要——因为它同时验证了三个核心差异点：在本地干活、不需要懂技术、看得到结果。

## Q7: Deskhand 最大的风险是什么？什么情况下会失败？

### 风险 1：用户的思维和操作习惯转变（最难）

普通人以前做任何事都是自己动手——自己打开 Excel 填数据、自己一张张整理照片、自己排版文档。现在要他们接受「我只说我要什么，让 AI 去做」，这是一个从未有过的操作方式。

难点不只是「知不知道这个产品」，而是「能不能接受这种工作方式」。

具体场景：一个行政人员要整理报销单，她习惯的方式是打开 Excel、一行行填。你告诉她「你只要说一句话，AI 就帮你填好了」，她的第一反应不是「太好了」，而是「它填的对吗？我怎么检查？万一错了谁负责？」——她不是不想省事，而是不知道怎么信任一个她看不懂的过程。

这意味着产品不能只是「能做到」，还要让用户「知道怎么让他做」「敢让它做」、「看得懂它在做什么」、「确认结果是对的」。

对于AI Native 的用户来说，这是一个非常自然的工作方式。我会先抛出提示词再一起协作讲清需求最后让他执行，但对于非 AI Native 的用户来说，他们可能没有兴趣写下第一句话，除非有”小红书视频“或者”演示文稿“告诉过他们，你需要的这个过程完整是这样的。

### 风险 2：Anthropic 自己做了

Cowork 已经在做类似的事。如果 Anthropic 继续往非技术用户方向迭代，Deskhand 的差异化窗口会越来越小。

但就像模型厂商不会自己去做所有产品一样，这个世界对产品的需求细分是很多的。Anthropic 可能占据 50-60%，但不能满足所有人——萝卜青菜各有所爱，他们在技术上领先，但总有一部分用户的需求没被满足到。

具体场景：Cowork 可能会做得越来越好，但它服务的是英语世界的主流用户。一个中国的小公司老板，他的文件是中文的、他的工作流是本地化的、他需要的集成是微信和钉钉而不是 Slack 和 Notion。这些细分需求 Anthropic 不会优先做。

### 风险 3：主动助理做不好会变成骚扰

主动发现需求是核心差异点，但做不好就是弹窗广告。

不过凡事都有双刃剑。对于不懂的人来说，有一个顾问主动提出「我帮你做点什么」，就好像实习生主动问你需不需要帮忙——他肯定会有提错的时候，但总比不提要好。关键是控制骚扰的度：少一点去打扰、找准时机再开口、让用户不需要花太多时间去看这些提议。

具体场景：用户刚打开电脑，Deskhand 弹出来说「你桌面有 47 个文件，要不要整理？」——如果用户正赶着开会，这就是骚扰。但如果用户刚忙完一天的事、电脑空闲了，同样的提醒就变成了贴心。时机和频率的把握，比提醒本身更重要。

## Q8: 三年后，Deskhand 会变成什么样子？

以前是「我去操作工具来完成任务」，现在是「我让 AI 去操作工具来完成任务」。就像特斯拉 FSD——你还是那个决定去哪的人，但你不再需要自己握方向盘了。

三年后，用户和 Deskhand 的关系是：我的工作，我来指挥，Deskhand 来操作。

**早上 9 点，打开电脑：**
Deskhand 告诉你：「你的邮箱里有 3 封客户邮件，我已经读过了，摘要在这里。另外上周你让我每周整理一次下载文件夹，我刚用访达把 23 个文件按类型分好了，有 2 个合同 PDF 看起来比较重要。」你说「邮件先放着，合同打开给我看」，它用预览打开那两个 PDF，高亮了关键条款。

**上午 10 点，做月报：**
你说「帮我用上个月的销售数据做一份月报，格式跟上次一样」。Deskhand 用访达找到你的销售 Excel，用 Python 跑了数据分析脚本生成图表，然后打开 Pages 把图表和文字排进上次的模板里，生成一份新文档。它把成品展示给你：「月报做好了，你看看。」你说「第三页的图表换成柱状图」，它回到 Python 脚本改了图表类型，重新导出，再更新到 Pages 里。

**下午 2 点，处理发票：**
你把手机拍的 20 张发票照片同步到电脑，说「帮我录入报销表」。Deskhand 用图像识别读取每张照片上的金额、日期、商户名，然后打开你的报销 Excel 模板，逐行填入数据。遇到一张模糊的它问你「这张金额是 3800 还是 8800？」你回答后它继续填完，最后把 Excel 保存好告诉你「20 张发票已录入，总金额 47,600，文件在桌面上」。

**下午 5 点，更新方案：**
你说「明天要跟客户开会，帮我把上次的方案更新一下」。Deskhand 用访达找到上次的 Keynote 方案，打开它，从你的数据文件夹里拉取最新数字替换掉旧的，重新生成了几页图表。它给你展示更新后的幻灯片：「数据已经换成最新的了，你看看哪里要调。」你说「这页重点突出增长率，字放大」，它回到 Keynote 调整排版，改完再给你看。

核心变化不是「AI 能做什么」，而是「人的工作方式变了」——从亲手操作每一步，变成描述意图、检查结果、做决策。手不再忙了，脑子还是你的。
