# Phase 2: 对话功能设计 Q&A

> 📅 2026-02-26 补写（Phase 2 在 2026-02 期间完成，这份文档回顾当时的设计思考）
> Phase 2 是 Deskhand 最核心也最大的功能模块，涵盖从消息输入到 Agent 调用再到流式渲染的完整链路。

---

## Q1: Claude Agent 的工作模式是什么？它会产生哪些类型的信息需要我们渲染？

在设计对话 UI 之前，得先搞清楚我们要对接的 Claude Agent SDK 到底是怎么工作的。它不是一问一答的聊天机器人，而是一个会自主循环执行任务的 Agent。

一次对话的典型流程是这样的：

用户发了一条消息之后，Agent 进入一个循环：

1. **思考（Thinking）**— 每一轮开始前，Agent 先内部推理：分析任务、评估复杂度、决定下一步策略
2. **决策** — 根据思考结果，走两条路：
   - 简单操作 → 直接调用工具（读文件、写文件、跑命令、搜索……）
   - 复杂子任务 → 派一个子代理（Sub-Agent）去处理，子代理有自己独立的思考和工具调用
3. **执行** — 工具返回结果，或子代理完成任务返回结果
4. **输出** — 向用户输出进度信息或阶段性结果
5. **回到第 1 步**，继续下一轮，直到整个任务完成

最后一轮结束时，Agent 输出一段总结性的文字回复。

整个过程是流式的——不是等全部做完再一次性返回，而是边做边往外推事件。SDK 通过 SSE 事件流把每一步都实时推给我们。所以我们的 UI 要渲染的，本质上就是这条事件流里的各种事件。

那这些事件怎么归类？想了三种方式：

**A. 按 SDK 原始事件类型分（技术视角）**
thinking、text_delta、text_complete、tool_use、tool_result、sub_agent_start、sub_agent_end、permission_request、error、complete……十几种事件，逐一映射到 UI 组件。好处是跟 SDK 一一对应不会漏，坏处是太碎了，用户不需要感知这么多状态。

**B. 按用户感知分 ✅**
站在用户角度，他们关心的其实就这几类：
- **等待状态** — AI 在思考，或者在两个工具调用之间的间隙
- **工具执行过程** — AI 读了什么文件、跑了什么命令、改了什么代码
- **子代理活动** — AI 派了个子任务去干活，里面有自己的工具调用链
- **最终回复** — 一段 Markdown 文字，任务的总结或回答

再加两个特殊情况：
- **权限请求** — AI 想执行危险操作（比如删文件、跑 shell 命令），需要用户点确认
- **错误/状态消息** — 出错了、被用户停止了、网络断了

**C. 按时间阶段分（响应前 / 响应中 / 响应后）**
按时间线切三段来组织。直观，但同一类信息（比如工具调用）会散落在不同阶段，组件不好复用。

**选了 B，理由：**

首先排除 A。SDK 的事件类型是给开发者用的技术协议，比如 text_delta 和 text_complete 本质上都是"AI 在说话"，tool_use 和 tool_result 本质上都是"AI 在用工具"——用户不需要也不应该感知这种粒度的区别。如果按 SDK 事件一一映射组件，UI 层会被迫跟 SDK 的协议细节耦合，以后 SDK 加个事件类型我们就得加个组件，这不合理。

再排除 C。按时间阶段分看起来直观（响应前显示 thinking，响应中显示工具调用，响应后显示文字），但实际上 Agent 的执行不是线性的——它可能思考完调用工具，工具返回后又思考，再调用另一个工具，中间还可能派子代理。同一种信息（比如"工具调用"）会出现在任何阶段，如果按阶段切，要么同一个组件在三个地方各写一遍，要么搞一堆条件判断。

B 的好处是：每一类对应一个 UI 组件，职责清晰。等待状态 → ProcessingIndicator，工具执行 → ToolActivityRow，子代理 → ActivityTree，最终回复 → ResponseCard，权限请求 → PermissionRequest，错误 → SystemMessage。组件之间不重叠，也不需要关心自己处于哪个"阶段"，只要事件流里出现了对应类型的事件，就渲染自己。这样不管 Agent 的执行顺序多复杂，UI 都能正确响应。

## Q2: 这些信息怎么组织成用户能看懂的界面结构？

Q1 确定了要渲染 6 类信息，现在问题是：这些东西在界面上怎么摆？

一次 Agent 执行可能产生几十个事件——3 次工具调用、1 个子代理（里面又有 5 次工具调用）、中间穿插思考、最后一段文字回复。如果把这些全平铺在聊天流里，会非常乱。

**A. 平铺消息流（像 Slack）**
每个事件都是一条独立消息，按时间顺序排列。简单直接，但一次复杂任务可能产生 20+ 条消息，用户消息会被淹没，找不到"AI 最终说了什么"。

**B. 按 Turn 分组，卡片式展示 ✅**
把用户一次提问到 AI 完整回复之间的所有事件，打包成一个"Turn"。一个 Turn 卡片里分两个区域：
- 上半部分：Activity 区（工具调用列表，可折叠）
- 下半部分：Response 区（最终文字回复）

Activity 区不是一个平铺列表，而是一棵树——因为子代理里面还有自己的工具调用：

```
Turn 卡片
├── Activity 区（可折叠）
│   ├── [✓] Read package.json
│   ├── [✓] Bash: npm install
│   ├── [↻] Task: 实现登录功能        ← 子代理
│   │   ├── [✓] Read auth.ts
│   │   ├── [✓] Edit auth.ts
│   │   └── [✓] Bash: npm test
│   └── [✓] Write README.md
└── Response 区（Markdown 文字回复）
```

用户可以折叠整个 Activity 区（只看回复），也可以折叠单个子代理节点（只看主流程）。

**C. 双栏布局（左聊天右操作日志）**
聊天在左边只显示文字对话，工具调用和执行过程放右边面板。信息分离很清晰，但用户视线要左右跳，而且右边面板跟我们已经规划的 ArtifactPanel 冲突。

**选了 B，理由：**

用户的心智模型是"我问了一个问题，AI 去做了一些事，然后给了我一个回答"——Turn 卡片正好对应这个心智模型。Activity 区默认可以折叠，不关心过程的用户直接看回复就行；想看细节的展开就好。

树形结构解决了子代理的嵌套问题：子代理本质上就是"一个工具调用里面又包含了一组工具调用"，用缩进和连接线表达父子关系，比平铺更容易理解层级。用户一眼就能看出哪些操作是主 Agent 做的，哪些是子代理做的。

排除 A 是因为信息密度太低——一次复杂任务产生 20+ 条消息，用户的提问和 AI 的最终回答会被淹没在中间过程里，找起来很痛苦。排除 C 是因为右边面板已经留给了 ArtifactPanel（显示文件预览、代码 diff 等），再塞一个操作日志进去会打架。

## Q3: AI 执行过程中用户看到什么？思考中、执行工具、等待结果，这些状态怎么呈现？

Q2 定了 Turn 卡片的结构，但卡片是最终形态。在 Agent 还在执行的过程中，用户盯着屏幕看到的是什么？

Agent 执行过程中有几种"等待"：

1. **刚发完消息，Agent 还没有任何输出** — 纯等待
2. **Agent 在两次工具调用之间思考** — 上一个工具完成了，下一个还没开始
3. **工具正在执行中** — 比如跑一个耗时的 bash 命令
4. **子代理在干活** — 主 Agent 在等子代理返回

怎么处理这些等待状态？

**A. 统一一个 "Thinking..." 动画**
不管 Agent 在干嘛，只要没有新内容输出，就显示 "Thinking..." + spinner。简单，但用户分不清 AI 是在想还是在干活，等久了会焦虑。

**B. 区分状态，但保持简洁 ✅**
- 纯等待 / 思考中 → 显示随机循环的等待文案（"Thinking..."、"Working..."、"Pondering..."）+ 读秒计时
- 工具执行中 → Activity 区实时出现新的工具行，带 spinner 图标表示正在执行
- 子代理干活 → 子代理节点展开，里面的工具行实时更新

关键是：用户不需要知道"Agent 在思考"和"Agent 在等工具返回"的区别，他们只需要知道"AI 还在干活，没卡死"。所以等待文案随机切换 + 读秒就够了，给人一种"它一直在忙"的感觉。

**C. 完全透明，显示内部状态**
把 Agent 的 thinking 内容也展示出来，让用户看到 AI 在想什么。信息量最大，但对非技术用户来说太吓人了，而且 thinking 内容经常是英文的技术推理。

**选了 B，理由：**

核心问题是解决用户的等待焦虑，而不是给用户看技术细节。

排除 A 是因为太单调——如果一个任务跑了 30 秒，用户盯着一个不变的 "Thinking..." 会觉得卡死了。随机切换文案（"Thinking..."→"Working..."→"Pondering..."）加上读秒计时（5s、12s、1:02），让用户感觉到"它一直在动，在忙"，心理上更容易等下去。

排除 C 是因为我们的目标用户是非技术人群。Agent 的 thinking 内容通常是英文的技术推理（"Let me analyze the file structure and determine..."），对非技术用户来说既看不懂也不想看，反而增加认知负担。

B 的巧妙之处在于：等待文案负责"AI 没卡死"的心理安慰，Activity 区的实时更新负责"AI 确实在做事"的进度感知。两者配合，用户既不焦虑也不无聊——看到工具行一条条冒出来，就像看进度条一样。

## Q4: AI 要在用户电脑上操作文件和执行命令，权限怎么设计？

这是 Deskhand 跟普通聊天产品最大的区别——AI 不只是说话，它真的会动你电脑上的东西。读文件还好，但如果 AI 要删文件、跑 shell 命令、改系统配置呢？

**A. 全部放行，不做权限控制**
用户既然选择用 Agent，就默认信任它。体验最流畅，但风险太大——AI 有时候会犯错，一个 `rm -rf` 就完了。对非技术用户来说更危险，因为他们可能看不懂 AI 要执行的命令。

**B. 全部拦截，每个操作都要确认**
任何工具调用都弹确认框。最安全，但体验极差——一个复杂任务可能有 20+ 次工具调用，用户要点 20 次"允许"，跟 UAC 弹窗一样烦。

**C. 按危险等级分层 ✅**
把工具分成两类：
- **安全操作**（读文件、搜索）→ 自动放行，不打扰用户
- **危险操作**（写文件、删文件、执行 bash 命令）→ 弹确认，让用户看到要做什么再决定

然后提供两种模式让用户自己选：
- **Ask 模式**：危险操作都要确认（默认）
- **Allow-all 模式**：只拦截真正的破坏性命令（rm、rmdir 等），其他自动放行

**选了 C，理由：**

A 不可能选。我们的用户是非技术人群，他们可能不知道 `rm -rf /` 意味着什么。AI 虽然大部分时候是对的，但它会犯错——尤其是理解错用户意图的时候。一个没有权限控制的 Agent 在非技术用户的电脑上跑，出事只是时间问题。

B 的问题是把安全做成了体验的敌人。一个"帮我整理下载文件夹"的任务，AI 可能要读 20 个文件、移动 10 个文件、创建 3 个文件夹——如果每一步都弹确认，用户会觉得这个工具比自己手动做还麻烦。UAC 弹窗的教训已经证明了：弹太多，用户会条件反射地点"允许"，权限控制反而形同虚设。

C 的分层设计让安全和体验各得其所。读文件、搜索这些操作不会造成破坏，自动放行不打扰用户；写文件、跑命令这些有风险的操作才弹确认。两种模式的设计是给不同阶段的用户：新用户默认 Ask 模式，每次都能看到 AI 要做什么，建立信任感；用了一段时间觉得 AI 靠谱的用户可以切到 Allow-all 模式提高效率，但即使在这个模式下，真正的破坏性命令（rm、rmdir）还是会拦住，兜底安全。

## Q5: 默认权限是严格还是宽松？怎么平衡安全和体验？

Q4 定了分层权限 + 两种模式，但还有一个问题：用户第一次打开 Deskhand，默认是哪个模式？

**A. 默认 Allow-all，让用户自己收紧**
开箱即用体验最好，AI 干活不会被打断。但新用户还没建立对 AI 的信任，第一次就看到 AI 在自己电脑上跑命令没有任何确认，会慌。

**B. 默认 Ask，让用户自己放宽 ✅**
新用户默认每次危险操作都要确认。前几次会觉得有点烦，但能看到 AI 每一步在做什么，逐渐建立信任。等用户觉得"这个 AI 挺靠谱的"，自己去切 Allow-all。

**C. 引导式，首次使用时让用户选**
第一次打开弹个选择："你希望 AI 每次操作前都问你，还是自动执行？"把决定权交给用户。但新用户根本不知道该选哪个——他们还没体验过 Agent，没有判断依据。

**选了 B，理由：**

安全产品的经典原则是"默认安全，允许放宽"——而不是反过来。

排除 A 是因为信任需要时间建立。用户第一次用 Deskhand，对 AI 能做什么、会不会犯错完全没概念。如果默认就放开权限，用户看到 AI 在自己电脑上跑命令、改文件，没有任何确认环节，第一反应不是"好方便"而是"好吓人"。更危险的是，万一 AI 第一次就犯了个错（比如理解错意图删了不该删的文件），用户对产品的信任直接归零。

排除 C 是因为新用户没有做选择的依据。他们还没体验过 Agent 的工作方式，不知道"每次确认"意味着什么频率，也不知道"自动执行"有什么风险。这时候让他们选，要么随便选一个（等于没选），要么焦虑地研究半天（糟糕的首次体验）。

B 的好处是让信任自然生长。新用户在 Ask 模式下，每次确认弹窗其实是一次"教育"——用户逐渐学会了 AI 会做哪些类型的操作（读文件、写文件、跑命令），也看到了 AI 每次都做对了。几次之后用户自然会想"每次都点允许好烦，我信任它了"，这时候主动切到 Allow-all 是一个知情的、有底气的选择。这比一开始就放开、出了事再收紧要健康得多。

## Q6: 输入栏需要哪些控制项？哪些进第一版？

用户跟 AI 对话不只是打字发消息。Agent 有很多可配置的东西——用什么模型、思考多深、在哪个目录干活、用哪些技能、权限模式……这些控制项都塞进输入栏吗？

**A. 极简，只有文本框 + 发送按钮**
像 ChatGPT 早期那样，什么配置都没有。最干净，但用户没法控制 AI 的行为，只能用默认配置。

**B. 全量，所有配置项都放进去**
模型选择、思考级别、工作目录、技能选择、工具选择、权限模式、附件上传……全部放在输入栏。功能最全，但输入栏会变成一个密密麻麻的控制面板，非技术用户看到就懵了。

**C. 分层，核心控制项进输入栏，其余放设置页 ✅**
输入栏只放跟"这次对话"直接相关的控制项：
- 模型选择（用哪个 AI）
- 思考级别（AI 想多深）
- 工作目录（AI 在哪个文件夹干活）
- 权限模式切换（Ask / Allow-all）
- 发送 / 停止按钮

技能选择、工具配置、API Key 管理这些不需要每次对话都改的，放到设置页。

**选了 C，理由：**

输入栏是用户每次对话都要面对的地方，它的信息密度直接决定了产品给人的第一感觉。

排除 A 是因为 Agent 不是普通聊天机器人——用什么模型、在哪个目录干活，这些直接影响 AI 的行为和结果。如果用户没法控制这些，遇到问题只能干瞪眼。比如用户想让 AI 整理桌面文件，但 AI 默认工作目录是 Home，用户连改都改不了。

排除 B 是因为控制项太多会吓跑非技术用户。一个输入栏里塞了 8 个按钮，用户的注意力会被分散——他们本来只想打字发消息，结果先要搞懂每个按钮是干嘛的。而且大部分配置项（技能、工具、API Key）不需要每次对话都改，放在输入栏是浪费空间。

C 的分层标准很简单：**这个配置项会不会在不同对话之间频繁切换？** 模型选择——会，简单问题用 Haiku 省钱，复杂任务用 Opus。思考级别——会，有时候要快有时候要深。工作目录——会，不同任务操作不同文件夹。权限模式——会，信任的任务开 Allow-all，敏感操作切回 Ask。这些都是"每次对话可能不同"的配置，放在输入栏随手可调。技能和工具配置是"设置一次很少改"的，放设置页合理。

## Q7: 数据从用户按发送到 AI 回复显示，技术上经过哪些环节？

前面几个问题定了"用户看到什么"，现在要想"技术上怎么实现"。Electron 有三个进程——渲染进程（React UI）、主进程（Node.js）、预加载脚本（桥梁）。数据怎么在这三层之间流动？

**A. 渲染进程直接调用 Agent SDK**
React 组件里直接 import Agent SDK，发消息、收事件都在渲染进程完成。最简单，但 Agent SDK 是 Node.js 模块，渲染进程跑在浏览器沙箱里，直接调用不了。而且把 API Key 暴露在渲染进程是绝对不能接受的用户安全问题。

**B. 通过 IPC 走主进程 ✅**
```
渲染进程（React）
  → preload 桥接层（contextBridge）
    → 主进程（Node.js）
      → Agent SDK → Claude API
      ← SSE 事件流
    ← IPC 事件推送
  ← Jotai atoms 更新
→ UI 重新渲染
```

渲染进程通过 preload 暴露的 API 发消息，主进程负责调用 Agent SDK，收到事件后通过 IPC 推回渲染进程，渲染进程更新 Jotai atoms 触发 UI 更新。

**C. 独立后端服务**
起一个本地 HTTP 服务，渲染进程通过 fetch 调用。架构最干净（前后端分离），但多了一层网络通信，而且 Electron 本身就有主进程可以跑 Node.js，没必要再起一个服务。

**选了 B，理由：**

这就是 Electron 的标准架构——渲染进程负责 UI，主进程负责系统级操作（文件、网络、SDK 调用），preload 做安全桥接。Agent SDK 是 Node.js 模块，天然跑在主进程里。IPC 是 Electron 内置的进程间通信，性能好、安全（API Key 不会暴露给渲染进程）。没有理由绕开这个现成的架构去造轮子。

排除 A 最核心的原因是安全：API Key 会暴露在渲染进程里，这对用户来说是绝对不能接受的安全问题。技术上渲染进程也调不了 Node.js 模块，但就算能调，光是 API Key 暴露这一条就足以否决。

排除 C 是因为从 vibe coder 的角度，架构越简单 AI 越不容易写出 bug。Electron 已经提供了主进程 + IPC 这套现成的方案，再额外起一个独立 HTTP 服务等于多了一层——多一个进程要管理、多一套错误处理、多一种通信协议。AI 在开发的时候要同时理解 Electron IPC 和 HTTP 两套通信方式，出错率会高很多。能用一套方案解决的事情，不要用两套。

## Q8: AI 会派子代理去处理复杂任务，这种嵌套怎么展示？

子代理跟普通工具调用不一样——普通工具调用是"做一件事就完了"（读个文件、跑个命令），子代理是"接了一个子任务，里面又有自己的一系列操作"。用户需要知道子代理在干嘛吗？展示到什么程度？

**A. 跟普通工具一样，只显示一行**
"Task: 实现登录功能 ✓"，不展开内部细节。最简洁，但用户看不到子代理在干嘛，如果子代理卡住了或出错了，用户不知道发生了什么。

**B. 可展开的嵌套树，默认折叠**
子代理显示为一行，可以点击展开看里面的工具调用。默认折叠保持简洁，但执行过程中用户只看到一行在转圈，等待焦虑又回来了。

**C. 默认展开，全部显示**
子代理的所有工具调用都展开显示。实时感最强，但如果子代理有 10+ 个工具调用，列表会很长，把 Response 区推得很远。

**D. 展示头几条，剩余折叠 ✅**
子代理默认展示前几条工具调用，剩余的折叠成"还有 N 项..."。用户能看到子代理在做什么（解决焦虑），但不会被一长串列表淹没。点击可以展开看全部。

**选了 D，理由：**

核心矛盾是：用户需要看到子代理在干嘛（否则等待焦虑），但又不能让子代理的细节喧宾夺主（否则信息过载）。

排除 A 是因为子代理往往是任务里最耗时的部分。如果只显示一行"Task: 实现登录功能"在转圈，用户不知道里面进展到哪了，跟 Q3 讨论的"AI 没卡死"的设计目标矛盾。

排除 B 跟 A 类似——默认折叠在执行过程中等于看不到进度。虽然用户可以手动展开，但这要求用户主动操作，而且展开后又变成了 C 的问题。

排除 C 是因为子代理的工具调用数量不可控。一个复杂子任务可能有 10-20 个工具调用，全部展开会把 Activity 区撑得很长，用户要滚动很久才能看到下面的 Response 区。主 Agent 的其他工具调用也会被推到视野之外。

D 的设计是：展示头几条让用户知道"子代理在做什么类型的事"，剩余的折叠不占空间。执行过程中新的工具调用冒出来，已完成的自然滚进折叠区，始终保持一个合理的展示长度。用户想看全部细节随时可以点击展开。这样既有实时感，又不会让界面失控。

## Q9: 出错了怎么办？各种错误场景用户看到什么？

Agent 在执行过程中有很多地方可能出错：网络断了、API 返回错误、AI 执行的命令失败了、用户主动停止了生成。这些情况用户应该看到什么？

**A. 统一一个错误提示**
不管什么错误，都显示"出错了，请重试"。最简单，但用户不知道发生了什么，也不知道该怎么办。网络断了和 API 额度用完了是完全不同的问题，处理方式也不同。

**B. 按错误类型分别处理 ✅**
不同的错误给不同的提示和样式：
- **网络错误** — "网络连接失败，请检查网络后重试"（红色）
- **API 错误**（额度用完、Key 无效等）— 显示具体原因 + 引导去设置页（红色）
- **工具执行失败**（命令报错）— 这个不算"系统错误"，AI 自己会处理（重试或换个方案），不需要特殊 UI
- **用户主动停止** — "已停止生成"（灰色，信息性提示，不是错误）
- **AI 内部错误**（SDK 异常）— "AI 遇到了问题，请重试"（红色）

**C. 错误全部静默，让 AI 自己处理**
Agent 有自我修复能力，工具失败了它会重试或换方案。不给用户看错误。但网络断了、API Key 无效这种 AI 自己也解决不了的问题，不告诉用户就会一直卡着。

**选了 B，理由：**

关键区分是"AI 能自己处理的错误"和"需要用户介入的错误"，这两类的处理方式完全不同。

工具执行失败（比如 bash 命令报错、文件不存在）属于 AI 能自己处理的——Agent 看到工具返回了错误，会自己决定重试还是换个方案。这种情况不需要弹错误提示吓用户，工具行上显示一个红色状态图标就够了，AI 会继续工作。

但网络断了、API Key 无效、额度用完这些，AI 自己解决不了，必须告诉用户。而且不能只说"出错了"——用户需要知道是什么问题、该怎么办。"网络连接失败"用户知道去检查 WiFi；"API Key 无效"用户知道去设置页重新配置。如果统一显示"出错了，请重试"，用户重试十次还是同样的错误，只会越来越沮丧。

用户主动停止单独处理，因为它不是错误——是用户的主动行为。用灰色信息提示"已停止生成"，不用红色，不要让用户觉得自己做错了什么。

## Q10: 这个功能很大，怎么拆成可以逐步交付验证的小块？

Phase 2 涵盖了 ChatArea、InputToolbar、Agent 调用、流式渲染、权限系统……一口气做完不现实，也没法验证。怎么拆？

**A. 按模块拆（先做完 ChatArea，再做 InputToolbar，再做 Agent）**
每个模块做完整再做下一个。问题是：ChatArea 做完了但 Agent 没接，用户看不到任何效果，没法验证。

**B. 按功能层拆（先做所有 UI，再接所有数据，再接 Agent）**
先把所有组件用 mock 数据跑起来，再一次性接真实数据。问题是：UI 和数据分开做，接的时候大概率对不上，要大量返工。

**C. 垂直切片，端到端逐步交付 ✅**
每一刀都切一个"从 UI 到 Agent"的完整功能：
1. 先跑通最小对话——发消息能收到 AI 纯文本回复（验证整条数据链路）
2. 加工具调用显示——能看到 AI 调用了什么工具
3. 加 Markdown 渲染——AI 回复有格式
4. 加停止按钮——能中断 AI
5. 加配置传递——模型选择、思考级别生效
6. 加权限系统——危险操作弹确认
7. 加子代理树形展示
8. 加错误处理
...每一步都是端到端可验证的。

**选了 C，理由：**

A 和 B 的共同问题是"做了一堆但看不到效果"。

按模块拆（A），ChatArea 做完了、InputToolbar 做完了，但 Agent 还没接——用户发消息没有任何响应，根本没法验证 UI 对不对。等到最后把 Agent 接上去，发现数据格式对不上、事件处理有 bug，要回头改一堆东西。做了两周才发现第一周的东西有问题，这个反馈周期太长了。

按功能层拆（B）更糟——先用 mock 数据把所有 UI 跑起来，看着挺好，但 mock 数据和真实的 Agent 事件流差别很大。真实的事件是流式的、顺序不确定的、可能有错误的，mock 数据模拟不了这些。等到接真实数据的时候，大概率要重写一半的 UI 逻辑。

C 的核心思路是：每一步做完都能 `bun run dev` 看到新东西。第一步做完，发消息能收到 AI 回复——整条数据链路（React → IPC → Agent SDK → Claude API → 事件流 → atoms → UI）就验证通了。后面每一步都是在这个已验证的基础上加东西，不会出现"拼不起来"的情况。

而且每一步的影响范围小——如果工具调用显示有 bug，只需要看 Step 2 改了什么，不用翻整个代码库。这对 vibe coding 特别重要：AI 每次只需要理解一小块上下文，出错率低，修起来也快。
