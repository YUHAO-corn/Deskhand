# Context Compacting MVP 复盘

> 日期：2026-04-07  
> 主题：Deskhand 上下文压缩第一版落地  
> 关键词：Agent、Compaction、任务记忆、用户偏好、长期可持续对话

---

## 这次我到底做了什么

这次做的事情，表面上看是在做“context compacting”，但本质上其实是在给 Deskhand 补一层 **工作记忆保护机制**。

原因很简单：长对话一多，agent 很容易出现一种很烦的状态，看起来还在继续聊，但其实已经开始忘记重点了。任务目标变模糊，用户偏好被冲掉，前面说过的话像是“还在”，但实际上模型已经抓不住。

所以这次我没有把重点放在“怎么压得更聪明”上，而是放在另一件更关键的事上：

**压缩之后，怎么把真正重要的东西补回来。**

这也是这轮实现里最重要的产品判断。

---

## 一开始的想法

最开始我们不是在追求一个特别复杂的压缩系统，而是在找一个足够实用的 MVP。

最后定下来的思路很朴素：

1. 不等上下文快爆了再压，而是在 70% 左右主动触发
2. 不相信压缩摘要能完整保留任务和偏好
3. 把“当前任务”和“用户长期偏好”放到 workspace 文件里
4. 压缩之后，再把这些文件重新注入回上下文

这套思路的核心不是“压缩”，而是“恢复”。

换句话说，Claude API 负责把上下文变短，Deskhand 负责把工作记忆补回来。

---

## 这次真正落地了哪些东西

### 1. 我把 workspace 级别的记忆文件体系搭起来了

现在每个工作目录下都会自动初始化：

- `.claude/tasks.jsonl`
- `.claude/user.md`
- `.claude/compact.md`

这三个文件分别承担三种职责：

- `tasks.jsonl`：记录任务状态、依赖关系、下一步动作
- `user.md`：记录用户长期偏好、角色、约束
- `compact.md`：放压缩提示词，让 compaction 更偏向“任务/偏好/下一步”

这一步很重要，因为这意味着 agent 的关键记忆第一次从“只活在上下文里”，变成了“落到 workspace 文件里”。

这不是一个小改动。它直接改变了 Deskhand 后续管理上下文的方式。

---

### 2. 我加了一套真正可调用的记忆工具

为了不让这些文件只是摆设，我又做了一组内置 MCP 工具：

- `TaskCreate`
- `TaskUpdate`
- `TaskList`
- `TaskGet`
- `UpdateUserPreference`

这组工具的意义，不是“多几个 API”，而是让 agent 在对话过程中真正有手段把记忆写下来。

也就是说，现在 agent 不只是“理论上可以记住”，而是已经有机制把这些东西存下来、查出来、更新掉。

从产品角度看，这一步让 Deskhand 的记忆系统开始从“模型能力”转向“产品能力”。

---

### 3. 我把 compaction 的运行时配置接进了 Agent

这次我没有另起一个复杂的中间层，而是直接把 compaction 配置接到了 `DeskhandAgent` 里。

当前实现里，4.6 系列模型会开启：

- `autoCompactWindow = 140000`
- `compact-2026-01-12` beta
- `context_management.edits = compact_20260112`

这意味着 Deskhand 现在已经能在运行时真正触发服务端 compaction，而不是停留在设计讨论阶段。

同时我还写了专门的 compaction prompt 文件，让压缩阶段更关注：

- 当前任务
- 用户偏好
- 最近几轮的关键决策
- 下一步该做什么

这件事看起来像“写了一份提示词”，但其实是在给 Deskhand 的压缩摘要定产品导向。

---

### 4. 我把 PostCompact 恢复链路接上了

这是我觉得这轮最关键的一步。

在压缩完成后，Deskhand 现在会读取：

- `.claude/tasks.jsonl`
- `.claude/user.md`

然后把它们整理成恢复上下文，再通过 `PostCompact` hook 注入回去。

这个设计的好处是：

- 不依赖摘要是否准确理解任务
- 不依赖摘要有没有改写用户原话
- 关键工作记忆是“原样恢复”，不是“二次总结”

这一步把“压缩后容易变笨”的风险，往下压了一大截。

---

### 5. 我把压缩前完整历史归档也补上了

后面又单独做了一步增强：在 `PreCompact` 的时候，把 SDK 提供的 transcript 原样复制到 workspace 下的 `.transcripts/`。

这意味着现在除了普通会话持久化之外，Deskhand 还会在压缩发生前，把完整历史另存一份。

这个能力的价值很现实：

- 方便事后排查 compaction 前到底聊了什么
- 方便做复盘、验收和问题定位
- 也方便以后做更强的历史回放能力

如果说前面的工作是在保护“当前工作记忆”，那这一步就是在保护“完整历史证据”。

---

### 6. 我顺手把 UI 默认模型切到了 4.6

因为这套 compaction 能力本身就是按 4.6 模型接的，所以我也同步把前端默认模型和模型选择器补到了 4.6。

这件事不复杂，但很必要。

否则功能虽然写好了，默认入口却还停在旧模型上，产品体验会是割裂的。

---

## 这次实现里，我比较满意的地方

第一，我没有把这件事做成“为了压缩而压缩”的工程项目。

真正落地的时候，方向始终很明确：不是追求更花哨的摘要算法，而是先保证 **压缩后还能继续工作**。

第二，我把“记忆”拆成了两种：

- 工作记忆：任务、偏好、下一步
- 历史记录：压缩前完整 transcript

这两个东西以前很容易混在一起，但它们其实不是一回事。前者是为了继续做事，后者是为了回看和复盘。

第三，这一版没有过度工程。

我没有一开始就做：

- 最近编辑文件恢复
- 最近 Skill 恢复
- 精细化 tool result 生命周期控制

这些都重要，但不是第一版闭环里最关键的。

---

## 还没做的东西

如果从最初的设计稿来看，现在已经完成的是一个很扎实的 MVP，但还不是完整形态。

还没做的主要有：

- 压缩后自动恢复最近编辑的关键文件
- 压缩后恢复最近 Skill 的上下文
- 更精细的 tool result clearing 策略
- 长对话下的整机人工验收

所以当前状态更准确的描述应该是：

**底层闭环已经跑通，增强层还没补齐。**

---

## 如果以后拿这个项目做面试 bullet，可以怎么讲

可以很实在地讲成这几条：

- 为桌面 AI Agent 设计并落地了第一版 context compacting 机制，目标是解决长对话中的任务漂移和偏好遗失问题
- 设计了 workspace 级工作记忆体系，把任务状态、用户偏好和压缩提示词落到 `.claude/` 文件中，而不是只依赖模型上下文
- 实现了一组内置记忆工具，让 agent 能在执行过程中持续记录和更新任务、偏好和依赖关系
- 在 Claude Agent SDK 上接入自动 compaction，并通过 `PostCompact` hook 恢复关键工作记忆，降低压缩后输出质量退化风险
- 增加压缩前 transcript 归档能力，将完整历史写入 `.transcripts/`，方便后续复盘、调试和质量分析

---

## 最后一句

这次不是做了一个“更会压缩”的系统。

更准确地说，是给 Deskhand 做了第一层真正意义上的 **抗遗忘能力**。

它还不豪华，但已经开始像一个能长期工作的 agent，而不只是一个上下文一长就失忆的聊天模型。
